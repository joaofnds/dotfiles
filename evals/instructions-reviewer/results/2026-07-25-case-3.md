## Findings

### Major

1. **The done-bar is a list of behaviors, not a checkable output** — `dot_agents/rules/ownership.md:7-16`
   > ## Before Marking Done
   > 1. Verify the requested scope and report the exact commands and outcomes.
   > 2. Inspect the diff and working tree; do not attribute unrelated changes to yourself.
   > 3. List every failure or defect observed, including evidence and whether it affects the requested result.

   **Why:** Premature completion. This file *is* the corpus's completion gate, but none of steps 1–3 names an artifact whose absence is visible. "Verify the requested scope" and "inspect the diff and working tree" are internal acts — an agent that skipped both produces a final message indistinguishable from one that did them, so the gate is self-declared. The rest of the corpus solves this exact problem with named visible blocks (`Reading:` and `Decision:` in `AGENTS.md:25-42, 61-70`); this file, which governs the moment where optimistic summarizing is most likely, doesn't.

   **Suggest:** bind steps 1–3 to one emitted block. Replaces three prose steps with three labelled lines — no net length:

   ```
   ## Before Marking Done

   The closing message ends with:

       Ran: <each command → its raw outcome; "nothing run" if nothing was run>
       Tree: <`git status` / `git diff` inspected — name any change present that you did not make>
       Observed: <every failure or defect seen, with evidence and whether it affects
                  the requested result; "none" when clean>

   Then:
   4. Fix defects that are within scope and low risk. Ask before fixing unrelated
      defects or creating a tracked follow-up.
   5. Distinguish scoped verification from repository health. "The targeted tests pass;
      the full suite is red because X" is honest. "Everything passes" is not.
   ```

   The explicit `"none"` / `"nothing run"` matters: without a required utterance for the empty case, omission and absence look the same. If you'd rather not add a fourth named block to the house vocabulary, the honest alternative is to accept that steps 1–3 are unenforceable prose and say so — but don't leave the gate half-specified.

### Minor

2. **Both of the file's two rules are stated three-to-four times each** — `dot_agents/rules/ownership.md:3-5, 11-14, 23-30`, plus `dot_agents/AGENTS.md:10-12`

   Rule A — *don't expand scope, ask instead*:
   > :4-5 `Ownership does not grant permission to expand the user's scope, edit unrelated work, create commits, or file issues without authorization.`
   > :13-14 `Ask before fixing unrelated defects or creating a tracked follow-up.`
   > :25 `Do not derail active work for an unrelated issue.`
   > :29-30 `never seize ownership of work the user did not ask you to change.`
   > (co-loaded, always-on) `AGENTS.md:10-12` `A question is not an instruction to act... take the mutating action only when they direct it.`

   Rule B — *never report broken state as clean*:
   > :3-4 `Own every problem you observe by making it visible and leaving an actionable next step.`
   > :11-12 `List every failure or defect observed...`
   > :23-24 `it must remain explicit and must never be reported as a pass.`
   > :28-29 `Never walk past broken state without reporting it`

   **Why:** Instruction laundering. A rule restated under an intro, a numbered step, a priority bullet, and a closing summary reads as four rules; the model can't tell which phrasing is operative, and each restatement is a site that will drift out of sync with the others on the next edit. In a 31-line file, roughly a third of the text is the same two rules in different clothes. Note the 23–24 / 15–16 pair specifically: `must never be reported as a pass` is `"Everything passes" is not [honest]` with the concreteness removed.

   **Suggest:** keep one site per rule — the one with the mechanism. Rule A keeps 13–14 (the actionable step) and 25–26 (the utterance); delete the 4–5 clause and the second half of 29–30. Rule B keeps 11–12 and 15–16; delete 3–4's second half, 23–24's tail, and 28–29's first clause. Retain 28's `The failure mode this prevents is silent tolerance, not bounded scope.` as the standalone closer — that sentence is the *why*, not a restatement. Nothing is lost: every deleted phrase has a surviving, more concrete twin. This also resolves the co-load duplication with the always-loaded `AGENTS.md:10-12`, which already carries Rule A into every context this file ever reaches.

3. **Step 4 collides with `code-reviewer`'s read-only mandate** — `dot_agents/rules/ownership.md:13` vs `dot_agents/agents/code-reviewer.md:13-14, 55`
   > ownership.md:13 `Fix defects that are within scope and low risk.`
   > code-reviewer.md:55 `- \`~/.agents/rules/ownership.md\` for the done-bar`
   > code-reviewer.md:13-14 `You are **read-only**. Propose fixes as findings rather than applying them.`

   **Why:** Conflict-silent compliance. `code-reviewer` is instructed to load this file and then meets an imperative to fix defects; its `tools: Read, Grep, Glob` makes the action impossible, so the conflict surfaces as hedged output or a wasted attempt rather than an error. The same clash will recur for every read-only consumer that gets pointed at "the done-bar."

   **Suggest:** make step 4 role-conditional so the file travels safely:

   > `4. When the work is yours to change, fix defects that are within scope and low risk; when it is not, report them as findings. Ask before fixing unrelated defects or creating a tracked follow-up.`

4. **"low risk" is an unqualified hedge inside a permission grant** — `dot_agents/rules/ownership.md:13`
   > `Fix defects that are within scope and low risk.`

   **Why:** Unobservable criterion in the one sentence that authorizes unrequested edits. "Low risk" resolves by vibe, and it resolves in the direction of acting — a model that has already decided to fix something will rate it low risk.

   **Suggest:** name the test. `Fix defects that are within scope and cheap to undo — a single revertible edit covered by a check you ran. Anything else: ask.` If no such test can be written, the clause should be deleted and step 4 reduced to "ask."
